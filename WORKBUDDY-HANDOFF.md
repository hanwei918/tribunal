# WorkBuddy project handoff

User constraints: starting from 2026-09-18; a team of three, each member has 1,000 activity credits in total; a single member's WorkBuddy and CodeBuddy usage is managed as one shared credit pool and must not be counted as 1,000 each; WorkBuddy is the primary development tool.
The project directory is fixed at `/Users/hanweizhou/Desktop/Tribunal`. Read WORKBUDDY-SCOPE.md first; do not attempt to read sibling directories outside the project.

Application design: a Python package `tribunal/`, using the standard-library unittest first, with a Streamlit interface (add the dependency at the UI stage), and the model accessed through a single adapter.
Pipeline: loader -> deterministic prepass/facts -> shared brief -> two advocates -> referee -> judge -> finalizer -> transcript/UI.
The default is one round of two advocate statements plus one judge pass, normally three LLM calls per case. Development credits and application inference costs are kept separate.

A case file has four top-level keys: `schema_version`, `case_no`, `dispute`, and `evidence`. All four keys must be retained; `case_no` is used to confirm that the requested case was loaded, and `schema_version` is used for contract compatibility checks.
A missing artifact must still retain its `evidence_id`; its `payload` is `null`, while `status: "MISSING"` and `weight_multiplier: 0.0` live inside that artifact's `admissibility` object.
During development, the public contract, the necessary index, and the policies may be read as permitted by `WORKBUDDY-SCOPE.md`. The bundle passed to a runtime Agent may contain only the public content of the selected case and the selected policies, and must not contain development documents or answer fields. Answers, corpus sources, historical handoffs, and manuals are not in this workspace and must not be requested or injected into a runtime prompt.
Amounts use Decimal; the confidence threshold is read from policy; every claim cites both an evidence id and a clause id.

One switch changes what the judge is given, and only when it is asked for. `--precedents` shows the judge up to three earlier closures a human reviewer made, chosen from `precedents/precedents.jsonl` because they share clauses with the case. They travel in the judge's user message as a `precedents` key: a fixed note and up to three items naming a `precedent_id`, a `category`, clause ids and a ruling — **no amount and no summary**. They are not evidence and not policy, and the note says so in its own words. With the switch off the key is absent and the message is the message it always was. The forbidden-key rejection applies to the block as well, at runtime as well as when an entry is written, and no field name from `loader.FORBIDDEN_KEYS` and none of `rationale`, `difficulty`, `governing_clauses`, `matched`, `expected` or `grade` may appear in an entry at all.

What actually exists: usable cases, policies, project documentation, and empty application directories; the application features and runtime API are not implemented yet. Take the current files, the actual API documentation, and the tests as authoritative.

Complete one acceptable module per round, read only the limited files, and report changes, tests, and open issues; do not automatically regenerate the whole project.
